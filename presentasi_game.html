POS 01 • BRIEFING ALGORITMA HYBRID • HMCDS VS AOA-SSA

Mengapa Memilih HMCDS (AOA + Markov Chain) Dibandingkan AOA-SSA?

Menjawab tantangan Dynamic Task Scheduling & Load Balancing secara proaktif dan ringan pada perangkat Fog–Cloud dibandingkan optimasi penempatan/replikasi file (Data Placement).

📁 AOA-SSA (Pembanding) Metaheuristic + Metaheuristic + Floyd
  • Fokus Kasus: Replikasi Data & Rute Jaringan Geografis (Data Placement — menentukan file populer $PD_i$ yang digandakan antar-DC).
  • Sifat Penanganan Beban: Reaktif & Struktural (tanpa mekanisme peramal probabilistik lonjakan CPU VM).
  • Keterbatasan di Node Fog: Overhead komputasi ganda (2 algoritma populasi AOA + SSA) ditambah matriks jarak terpendek Floyd ($O(V^3)$).
🚀 HMCDS: AOA + Markov Chain (Pilihan Kita) Stochastic Forecasting + Metaheuristic
  • Fokus Kasus: Dynamic Task Scheduling & Load Balancing (penjadwalan ribuan tugas CPU IoT Real-Time & Non-RT ke VM).
  • Alur Kerja Proaktif: IoT Tasks → Prediksi Status VM (Markov P_ij) → Optimasi Mapping (AOA).
  • Sangat Ringan di Fog: Sifat Memoryless Markov ($O(1)$ tanpa histori panjang) + hasil teruji: -11,72% Delay, -8,29% Makespan, +4,66% PIR.

Kondisi / Skenario Sistem Output HMCDS (AOA + Markov Chain) — Pilihan Utama Output AOA-SSA — Pembanding
1. Karakteristik Workload Beban Kerja Dinamis & Real-Time IoT: Memisahkan tugas Real-Time (Fog) vs Non-RT (Cloud) & meramal lonjakan beban CPU VM. Manajemen Penyimpanan (Data Replication): Menentukan duplikasi file populer & lokasi simpannya di data center.
2. Pencegahan Server Penuh Proaktif & Prediktif: Matriks transisi Markov ($P_{ij} \ge \text{MAX}$) memigrasikan tugas ke VM Low-Load sebelum macet. Reaktif & Struktural: Pencarian populasi ganda (AOA+SSA) tanpa prediksi peluang status beban VM di masa depan.
3. Skalabilitas Tugas Besar Cepat & Hemat Energi: Makespan -8,29%, Delay -11,72%, dan jadwal 1.000 tugas tuntas dalam 13,41 detik. Overhead Lebih Kompleks: Menggabungkan 2 metaheuristik (AOA+SSA) + algoritma shortest path Floyd.
4. Beban Memori di Fog Node Ringan (Lightweight): Sifat memoryless Markov tidak butuh histori panjang; ideal untuk Fog VM (RAM 0,5 GB). Butuh Topologi Global: Wajib menyimpan matriks jarak antar-node (Floyd), popularitas file ($PD_i$), & storage region.

POS 02 • LAPISAN 1: IOT SENSOR VALLEY • LATAR BELAKANG

Hybrid Markov Chain-Based Dynamic Scheduling (HMCDS)

Judul Jurnal: "Hybrid Markov chain-based dynamic scheduling to improve load balancing performance in fog-cloud environment"
Penulis: Navid Khaledian, Shiva Razzaghzadeh, Zeynab Haghbayan, & Marcus Völp (University of Luxembourg & Islamic Azad University)
Publikasi: Sustainable Computing: Informatics and Systems (Elsevier), Vol. 45, Article 101077, 2025 • doi:10.1016/j.suscom.2024.101077

Mengapa Fog–Cloud? Pada ekosistem IoT, jika semua data dikirim ke Cloud Data Center yang jarak fisiknya jauh, maka latensi (waktu tunda) menjadi sangat tinggi. Karena itu digunakan Fog Computing di tepi jaringan (dekat sensor). Namun, server Fog memiliki kapasitas CPU & RAM terbatas sehingga tanpa penjadwalan cerdas akan muncul 3 masalah utama:

1. Load Instability

Distribusi tugas tidak merata sehingga node Fog tertentu mengalami bottleneck (macet total) saat lonjakan data IoT.

2. Makespan & Delay Tinggi

Waktu selesai total (makespan) dan antrean membengkak; sangat berbahaya bagi aplikasi real-time (medis, mobil otonom, pabrik).

3. Underutilization of VM

Sebagian Virtual Machine (VM) overload sedangkan VM lain menganggur (idle), menyebabkan pemborosan energi listrik.

🎙️ PANDUAN PENJELASAN PRESENTER (SLIDE 2)
"Jurnal ini mengusulkan kerangka kerja HMCDS untuk menjawab dilema IoT: Cloud itu besar tapi jauh (latensi tinggi), sedangkan Fog itu dekat tapi kecil (mudah penuh). HMCDS menggabungkan Markov Chain untuk meramal VM mana yang akan penuh lebih dulu, dan AOA untuk membagi tugas secara optimal agar tidak ada VM yang overload."
POS 03 • GERBANG CF_MANAGER • ARSITEKTUR 3 LAPIS

Three-Layer Architecture & Klasifikasi Tugas oleh CF_Manager

1. IoT / Sensor Layer

Lapisan paling bawah tempat sensor & perangkat pintar menghasilkan ribuan permintaan tugas (tasks) dengan ukuran dan tenggat waktu berbeda-beda.

2. Fog Layer (CF_Manager)

Terdiri dari 15 VM (kecepatan 100–2.800 MIPS, RAM 0,5 GB, Storage 10 GB, Bandwidth 1 GB/s). Di sini CF_Manager bertindak sebagai broker pengatur tugas.

3. Cloud Layer

Terdiri dari 2 Data Center, 4 Host, 40 VM (kecepatan tinggi 3.000–5.000 MIPS, RAM 1 GB, Storage 20 GB, BW 0,5 GB/s) untuk tugas berat & backup.

3 Kriteria Klasifikasi Tugas oleh CF_Manager (Task Scheduler):

1. Berdasarkan Urgensi (Deadline):
  • Real-Time Tasks: Tenggat ketat, wajib diproses di Fog Layer terdekat agar latensi minimal.
  • Non-Real-Time Tasks: Toleran jeda (agregasi/background), boleh dikirim ke Fog maupun Cloud.
2. Kebutuhan Sumber Daya:
  • Lightweight (Ringan): Dieksekusi langsung di node edge / fog.
  • Heavyweight (Berat): Dialokasikan ke Fog VM ber-MIPS besar atau ke Cloud Layer.
3. Ketergantungan (Dependency):
  • Independent: Tidak saling tunggu, bisa dijadwalkan paralel.
  • Dependent: Memiliki urutan proses, dimodelkan dengan Directed Acyclic Graph (DAG).

POS 04 • FOG PLATEAU • TAHAP 1: MARKOV CHAIN

Tahap 1: Prediksi Beban VM dengan Markov Chain (VM Load Forecasting)

Mengapa Markov Chain? Markov Chain adalah model peluang yang bersifat memoryless (prediksi kondisi masa depan $t+1$ hanya butuh kondisi saat ini $t$, tanpa perlu menyimpan sejarah panjang). Hasilnya: prediksi beban VM berjalan sangat cepat & ringan dibanding harus melatih Deep Learning.

Rumus 1 — Menghitung Beban Tugas & Total Beban VM: $$L_i(t) = \lambda_1 E_i(t) + \lambda_2 W_i(t), \quad \text{LOAD}(i) = \sum_{k=1}^{n} L_k(t)$$
• $L_i(t)$: Beban dari 1 tugas ke-$i$ pada waktu $t$.
• $E_i(t)$: Waktu eksekusi tugas • $W_i(t)$: Waktu tunggu tugas di antrean.
• $\lambda_1, \lambda_2$: Bobot prioritas (total $\lambda_1 + \lambda_2 = 1$).
• $\text{LOAD}(i)$: Total akumulasi beban seluruh $n$ tugas yang sedang dikerjakan di VM ke-$i$.
Rumus 2 — Tiga Status Beban VM & Ambang Batas:
  • V2 = U (Underloaded / Low-Load): Beban di bawah batas $\text{MIN}(i)$ → VM masih longgar, prioritas utama penerima tugas baru/migrasi.
  • V1 = N (Normal Load): Beban di rentang $\text{NORMAL}(i)$ → VM bekerja stabil.
  • V3 = O (Overloaded / High-Load): Beban melewati batas $\text{MAX}(i)$ → VM kepenuhan, terancam macet!
Rumus 3 — Matriks Probabilitas Transisi Status VM ($P_{ij}$): $$P_{ij}(t) = P\{X_{n+1} = j \mid x_n = i\}, \quad \sum_{j=1}^{N} a_{ij} = 1 \qquad\text{dan multi-langkah:}\qquad P_{ij} = \sum_{t=2}^{n} \frac{P_{ij}^{(t)} + P_{ji}^{(t)}}{2}$$
• Cara Baca Rumus: $P_{ij}(t)$ adalah peluang sebuah VM yang saat ini berada di status $i$ ($x_n = i$, misalnya Normal) akan berpindah ke status $j$ pada langkah berikutnya ($X_{n+1} = j$, misalnya menjadi Overloaded).
• Aturan Keputusan Migrasi: Jika sebuah VM diprediksi memiliki peluang tinggi menuju Overloaded ($P_{ij} \ge \text{MAX}(d_i)$), maka sebelum VM itu benar-benar macet, sistem langsung memblokirnya dari tugas baru dan memigrasikan sebagian tugasnya ke VM yang diprediksi Low-Load ($P_{ij} \le \text{MIN}(d_i)$).
🎙️ PANDUAN PENJELASAN PRESENTER (SLIDE 4 — RUMUS MARKOV)
"Untuk menjelaskan rumus di slide ini cukup 3 poin: Pertama, kita ukur dulu beban tiap VM ($\text{LOAD}$) dari waktu proses ($E_i$) ditambah waktu antre ($W_i$). Kedua, setiap VM diberi label status: Low-Load (longgar), Normal, atau Overloaded (penuh). Ketiga, matriks $P_{ij}$ menghitung peluang apakah VM yang sekarang Normal sebentar lagi akan berubah jadi Overloaded. Kalau peluang $P_{ij}$-nya melewati batas MAX, tugasnya langsung dipindahkan lebih dulu ke VM yang Low-Load."
POS 05 • FOG PLATEAU • TAHAP 2: ARITHMETIC OPTIMIZATION ALGORITHM

Tahap 2: Optimasi Penjadwalan Menggunakan AOA

Setelah Markov Chain menyaring VM mana yang aman (tidak Overloaded), AOA bertugas mencari kombinasi pemetaan Tugas ke-$i$ → VM ke-$j$ yang menghasilkan waktu selesai paling cepat dan hemat energi menggunakan 4 operasi matematika dasar ($\div, \times, -, +$).

Rumus 1 — Fungsi Tujuan / Fitness Function (Apa yang Ingin Diminimalkan?): $$\text{ETC}_{ij} = \frac{T_{len}^i}{VM_{pow}^j} \qquad | \qquad \text{Cost}_{\text{fog}} = \min \left( \max_{j \in \{1..m\}} \sum_{i=1}^{n} \text{ETC}_{ij} \right) \qquad | \qquad F = \alpha \cdot D + (1 - \alpha) \cdot E$$
• $\text{ETC}_{ij}$ (Expected Time to Compute): Estimasi waktu eksekusi tugas $i$ di VM $j$, yaitu panjang instruksi tugas ($T_{len}^i$ dalam MI) dibagi kecepatan CPU VM ($VM_{pow}^j$ dalam MIPS).
• $\text{Cost}_{\text{fog}}$: Tujuan di lapisan Fog (Real-Time) adalah meminimalkan Makespan (waktu selesai pada VM yang paling terakhir rampung).
• $F$: Tujuan gabungan di Fog–Cloud (Non-Real-Time) adalah meminimalkan kombinasi Delay ($D$) dan Konsumsi Energi ($E$) dengan bobot $\alpha \in [0,1]$.
Rumus 2 — Pengendali Fase Pencarian ($\text{MOA}$ dan $\text{MOP}$, dengan $\alpha = 5$): $$\text{MOA}(C\_Iter) = \text{Min} + C\_Iter \times \left( \frac{\text{Max} - \text{Min}}{M\_Iter} \right) \qquad\text{dan}\qquad \text{MOP}(C\_Iter) = 1 - \frac{C\_Iter^{1/\alpha}}{M\_Iter^{1/\alpha}}$$
• $\text{MOA}$ (Math Optimizer Accelerated): Nilainya naik bertahap dari iterasi awal ($C\_Iter=1$) hingga iterasi akhir ($M\_Iter=30$). Di awal iterasi $\text{MOA}$ masih kecil sehingga algoritma fokus Eksplorasi; di akhir iterasi $\text{MOA}$ besar sehingga fokus Eksploitasi.
• $\text{MOP}$ (Math Optimizer Probability): Mengatur seberapa besar langkah perubahan posisi solusi di setiap iterasi.
Rumus 3a — Fase Eksplorasi ($r_1 > \text{MOA}$) — Global ($\div, \times$): $$X_{i,j} = \begin{cases} best(x_j) \div (\text{MOP} + \epsilon) \times S_j, & r_2 < 0.5 \\ best(x_j) \times \text{MOP} \times S_j, & r_2 \ge 0.5 \end{cases}$$

Karena pembagian ($\div$) & perkalian ($\times$) mengubah angka secara drastis, operator ini dipakai untuk melompat jauh menjelajahi kandidat VM baru di seluruh jaringan.

Rumus 3b — Fase Eksploitasi ($r_1 \le \text{MOA}$) — Lokal ($-, +$): $$X_{i,j} = \begin{cases} best(x_j) - \text{MOP} \times S_j, & r_3 < 0.5 \\ best(x_j) + \text{MOP} \times S_j, & r_3 \ge 0.5 \end{cases}$$

Karena pengurangan ($-$) & penjumlahan ($+$) mengubah angka secara halus, operator ini dipakai untuk memoles solusi terbaik best(x). ($S_j = (UB_j - LB_j)\mu + LB_j$).

🎙️ PANDUAN PENJELASAN PRESENTER (SLIDE 5 — RUMUS AOA)
"Inti rumus AOA sangat intuitif: kalau sebuah angka kita kali atau bagi ($\times, \div$), nilainya akan meloncat jauh — itulah kenapa dipakai di awal untuk Eksplorasi mencari kandidat VM secara luas. Sebaliknya, kalau angka kita tambah atau kurang ($+, -$), nilainya hanya bergeser sedikit — itulah kenapa dipakai di akhir untuk Eksploitasi menyempurnakan jadwal terbaik best(x)."

📚 Glosarium & Contekan Jawaban Tanya Jawab (Q&A):

  • Apa beda peran Markov Chain dan AOA di HMCDS?
    Jawaban: Markov Chain bertugas sebagai peramal beban (mendeteksi VM yang akan Overloaded dan memigrasikan bebannya lebih awal), sedangkan AOA bertugas sebagai pengambil keputusan penjadwalan (memetakan tiap tugas ke VM yang lolos filter Markov agar Makespan, Delay, & Energi minimum).
  • Apa itu Makespan, Delay, dan Throughput?
    Jawaban: Makespan adalah total waktu sejak tugas pertama mulai dikerjakan sampai tugas paling terakhir selesai. Delay adalah waktu tunda sejak sensor mengirim tugas hingga selesai diproses. Throughput adalah jumlah tugas yang tuntas per satuan waktu ($\sum \text{ExeTime}(t_i)$).
  • Bagaimana rumus menghitung PIR (Performance Improvement Rate)?
    Jawaban: $\text{PIR}(\%) = \frac{Y - Y'}{Y} \times 100\%$, di mana $Y$ adalah nilai metrik algoritma pembanding dan $Y'$ adalah nilai metrik HMCDS.
  • Mengapa tidak memakai Deep Learning saja untuk prediksi beban VM?
    Jawaban: Karena node Fog memiliki CPU & RAM terbatas (100–2.800 MIPS, RAM 0,5 GB). Sifat Memoryless pada Markov Chain membuat prediksi berjalan instan tanpa beban komputasi pelatihan model yang berat.
